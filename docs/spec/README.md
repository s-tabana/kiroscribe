# Kiroscribe の仕様一覧

Kiroscribe の振る舞いを、確かめられる単位で 1 項目ずつ書き出したものです。すべての項目を自動テストかリリース前の実機チェックに結び付け、結び付いていない項目があれば CI が失敗するようにしています。読者は開発者です。アプリの使い方は [guide.md](../guide.md) にあります。

機能を足す・直すときの手順（仕様の項目を書く → テストを書く → 実装する）は、[development.md](../development.md) の「仕様とテスト」にあります。

## 項目の読み方

各項目は、領域ごとのファイルに次の形で書きます。数値（4 秒、20 秒、6 時間など）と文言は、コードの値です。

```text
- **ID** ［確かめ方の種類］〔印〕 〜のとき、〜する。
```

**ID** は「領域の接頭辞 + ハイフン + 3 桁の番号」です（例: `NOTE-001`）。接頭辞は、ファイルの名前（`note.md` なら NOTE）と同じにします。一度付けた ID は、文を直しても変えません。項目をなくしたときは、その ID を [retired.txt](retired.txt)（欠番の一覧）に移し、番号は使い回しません。

**確かめ方の種類** は、その項目を確かめる方法です。「・」で区切って複数書いたときは、それぞれの方法で確かめます。

| 種類 | 内容 | 検査が求めるもの |
| --- | --- | --- |
| 単体 | Rust の部品のテスト、画面（React）の部品のテスト。外部とは通信しない | その ID を参照するテスト |
| 結合 | 模擬のサーバー（OpenAI・Anthropic・GitHub の代わり）、ファイルのデータベース、実際の OS の機能を相手にするテストと、本体のコマンドの層を通すテスト | その ID を参照するテスト |
| E2E | 実際のアプリを起動して、画面を操作するテスト | `e2e/` の下のテストからの参照 |
| 手動 | 実機でしか確かめられないもの（実際のマイク、実際の会議アプリ、Windows へのインストール・自動起動、実際の API、実際の更新） | [リリース前の実機チェックリスト](../release-checklist.md)への記載 |
| 未検証 | 自動テストでも実機チェックでも確かめていないもの（ほかの種類と一緒には書かない） | なし |

**印** は、付いている項目だけにあります。

| 印 | 意味 |
| --- | --- |
| 〔見直し予定〕 | いまの振る舞いを書いてあるが、変えることを考えている |
| 〔実装待ち〕 | 決まった振る舞いを書いてあるが、実装がまだ追いついていない。項目のすぐ下の「実装待ち」の行に、いまの状態を書く。[未対応の一覧](pending.txt)に載せ、実装とテストがそろったら、印・行・一覧の 3 つを消す |

## テストとの結び付け

テストの名前（Rust は直前のコメント）に、仕様の ID を角かっこで書きます。1 つのテストが複数の項目を確かめるときは、続けて書きます。

```rust
// [NOTE-004][NOTE-007]
#[test]
fn list_notes_newest_first_with_preview() { /* … */ }
```

```ts
it("[NOTE-014] 確認してからノートを削除し、次のノートを選ぶ", async () => { /* … */ });
```

- Rust: `#[test]`・`#[tokio::test]` の付いた関数の直前に続くコメント（`//`・`///`）に書きます。関数の名前は変えません。
- vitest・node:test・E2E: `it(…)`・`test(…)` の名前の文字列に書きます（`it.each(表)("[ID] …", …)` の形も拾います）。
- `#[ignore]`、`.skip`、`.todo` のテストは、数えません。
- 置き場所で層を分けます。`e2e/` の下は E2E、`src-tauri/` の下は本体のコマンドの層、それ以外（`crates/`、`src/`、`scripts/`）は単体・結合です。

## 予定の仕様

まだ実装していない機能の仕様は、[planned/](planned/) に、同じ書き方で置きます。検査（`check-spec-coverage.mjs`）は、このフォルダを読みません。作る順番は、[開発の計画](../plan.md)にあります。

| 接頭辞 | 領域 |
| --- | --- |
| CMP | [会議の相棒](planned/cmp.md) |
| IDX | [資料の索引](planned/idx.md) |
| CONN | [サービスの接続](planned/conn.md) |

- 実装する PR で、項目を `docs/spec/` の同じ名前のファイルに移し、テストと一緒に入れます。ID は変えません。
- 移す前に、その項目に関わる未決の点（各ファイルの末尾）を決めます。決めた案は項目の文に反映し、未決の節は `docs/spec/` に移さずに消します。
- 予定の仕様の接頭辞と ID は、`docs/spec/` のほかの項目に使いません。
- `docs/spec/` の項目の文は、まだ移していない予定の項目を参照しません。後の段階で関わる部分は、その段階の PR で文に足します（[開発の計画](../plan.md)の「段階をまたぐ項目」）。

予定の仕様を直す PR では、検査の対象外であることを補うため、次を確かめます。

- 各ファイルを `parseSpecFile`（`scripts/check-spec-coverage.mjs`）で読み、問題が出ないこと（接頭辞とファイル名がそろうことを含む）。
- ID が、`docs/spec/` の項目・[retired.txt](retired.txt)・ほかの予定の仕様と重ならないこと。
- 文の中で参照している ID が、すべて仕様一覧か予定の仕様にあること。
- [開発の計画](../plan.md)の表で、すべての項目がちょうど 1 つの PR に割り当てられていること。

## 未対応の一覧

[pending.txt](pending.txt) は、求めるテストがまだそろっていない項目の一覧です。検査は、ここに載っている行だけ見逃します。**この一覧は、減らすだけにします。** テストを書いたら行を消し（消し忘れると検査が失敗します）、検査を通すために行を足すことはしません。`node scripts/check-spec-coverage.mjs --strict` は、一覧を見逃しに使わずに、残っている行をすべて不足として数えます（リリースのワークフローは、こちらで検査します）。
