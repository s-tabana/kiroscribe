# REL: 配布とリリース

インストーラと、リリースを作る手順。

- **REL-001** ［E2E・手動］ 配布するのは Windows（64 ビット）のインストーラ `Kiroscribe_<バージョン>_x64-setup.exe`。管理者の権限なしで、利用者ごとの場所（`%LOCALAPPDATA%\Kiroscribe`）にインストールできる。インストーラの言語は日本語と英語。
- **REL-002** ［手動］ コード署名をしていないため、インストーラの実行時に SmartScreen の警告が出ることがある。「詳細情報」→「実行」でインストールできる。
- **REL-003** ［単体］ リリースの前に、バージョンの書き間違いを検査する。package.json・Cargo.toml（[workspace.package]）・tauri.conf.json のバージョンが同じであること、タグを指定したときはタグが「v<バージョン>」であることを確かめ、食い違いはまとめて知らせる。問題がなければバージョンだけを出力する。
- **REL-004** ［単体］ リリースの本文は、CHANGELOG.md のそのバージョンの節の本文（見出しの行は除く）を使う。節がない、本文が空のときは、エラーにしてリリースを止める。バージョンは全体が一致する節だけを選ぶ（0.2 や 0.2.0-beta.1 は 0.2.0 と別物）。改行が CRLF でも同じ結果になり、コードブロックの中の「## 」は節の区切りにしない。
- **REL-005** ［単体］ アプリが更新を見つけるための latest.json は、バージョン・リリースの本文・公開日時・Windows 用の署名とインストーラの URL（GitHub のリリースの URL）を持つ。バージョン・リポジトリ名・ファイル名・日時の形が正しくないとき、署名が空・形式違い・別のファイルや別のバージョンのものであるときは、作らずにエラーにする。
- **REL-006** ［単体］ リリースを公開する前に、ビルドしたインストーラの署名を、アプリに埋め込む公開鍵と、1 つ前のリリースに埋め込まれていた公開鍵（利用者のアプリが信頼している鍵）の両方で検証する。ファイルが 1 バイトでも違う、別の鍵で署名されている、署名に書かれたファイル名・バージョンが書き換えられている場合は、公開を止める。
- **REL-007** ［単体］ アプリ内の更新に必要な設定（更新用のファイルを作ること、取得元の URL、1 行の公開鍵、利用者の操作なしで進むインストールの方式）がそろっている。
- **REL-008** ［単体］ 「v<バージョン>」のタグを push すると、検査・テスト（本物のインストーラでのインストールと更新の通しのテストを含む）・署名付きのビルド・署名の検証を経て、インストーラ・署名・latest.json・SHA256SUMS.txt を付けたリリースが公開される。ハイフンの付くバージョン（0.3.0-beta.1 など）はプレリリースになり、利用者のアプリには配られない。
- **REL-009** ［E2E］ Kiroscribe を入れたことがない Windows に、インストーラで入れて起動できる。すでに入っている PC に新しいインストーラを実行すると、ノートと設定を残したまま新しいバージョンになる。
- **REL-010** ［E2E］ インストーラで入れると、「アプリと機能」の一覧に「Kiroscribe」がそのバージョンで載り、スタートメニューにショートカットができ、アンインストーラが置かれる。実行ファイルには、そのバージョンが埋め込まれている（ファイルのプロパティの「製品バージョン」）。
- **REL-011** ［E2E］ アンインストールすると、アプリ・「アプリと機能」の一覧の項目・ショートカットが消える。ノートなどのデータ（`%APPDATA%\dev.kiroscribe.desktop`）は残す（消すかどうかは、アンインストーラの画面で利用者が選ぶ）。
- **REL-012** ［単体］ リリースを公開した直後に、利用者のアプリが見る latest.json（`https://github.com/s-tabana/kiroscribe/releases/latest/download/latest.json`）が新しいバージョンを指し、そこに書かれた URL から取得したインストーラが、ビルドしたものと同じ（SHA-256 が SHA256SUMS.txt と一致する）で、latest.json の署名がアプリに埋め込む公開鍵と 1 つ前のリリースの公開鍵の両方で検証できることを確かめる。プレリリースでは、利用者のアプリが見る latest.json がそのバージョンを指していないことを確かめる。公開の直後は配信に時間がかかり、同じタグで実行し直した直後は配信のキャッシュに新旧のファイルが混ざることがあるため、公開したファイルどうしの食い違い（.sig と latest.json の署名、署名の検証）も含めて、数分のあいだ確かめ直す。確かめられなければ、リリースをプレリリースに戻して（利用者のアプリに配られないようにして）、失敗にする。
